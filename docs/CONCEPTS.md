# 핵심 개념: Linux 서버 관제를 처음 이해하는 순서

각 항목을 **정의 → 동작 원리 → 이 프로젝트의 실제 코드** 순서로 읽는다. 명령을 외우기보다 어떤 시스템 상태가 변하는지 이해하는 것이 목표다.

## 1. 프로세스, 사용자와 권한

**프로세스(process)**는 실행 중인 프로그램이다. 운영체제는 각각에 PID(프로세스 ID)와 실행 사용자(UID)를 부여한다. 사용자마다 접근할 수 있는 파일과 프로세스가 다르다.

- **Root**는 대부분의 시스템 설정을 바꿀 수 있는 특권 계정이다. 앱을 Root로 실행하면 앱 취약점이 곧 높은 시스템 권한으로 이어질 수 있다.
- **일반 사용자**는 자신에게 허용된 작업만 수행한다. `provision.sh`는 시스템을 설정할 때만 Root가 필요하고, `run-app.sh`와 `monitor.sh`는 `agent-admin`으로 실행한다.
- `id agent-admin`, `ps -ef`, `pgrep -u <UID> -f '<패턴>'`으로 UID와 PID를 검증한다. `pgrep -f`는 프로그램 이름뿐 아니라 실행 명령줄도 검사한다. 이 때문에 코드에서는 허용한 앱 이름 패턴으로 제한한다.

## 2. 그룹과 전통적 권한(소유자/그룹/그 외)

Linux 파일에는 **소유 사용자(owner)**, **소유 그룹(group)**, **그 외(others)**의 읽기(`r`), 쓰기(`w`), 실행(`x`) 권한이 있다. 디렉토리에서는 `x`가 **진입/경로 탐색**, `r`가 **이름 목록 읽기**, `w`가 **항목 생성·삭제**에 관여한다.

- `chmod 750 file`: 소유자 `rwx`=7, 그룹 `r-x`=5, 기타 `---`=0. 이 값은 `monitor.sh`에 적용한다.
- `agent-common`에는 admin/dev/test가, `agent-core`에는 admin/dev만 속한다. QA 계정은 업로드 자료를 다뤄야 하지만 비밀 키와 운영 로그를 수정하면 안 되기 때문이다.
- `upload_files`는 `agent-common:2770`, `api_keys`와 `/var/log/agent-app`는 `agent-core:2770`이다. 앞의 **2(setgid 비트)** 때문에 그 디렉토리에 새로 만드는 항목은 보통 디렉토리의 그룹을 이어받는다.

단순 `chmod 777`을 쓰면 모든 로컬 사용자가 비밀 영역을 바꿀 수 있어 최소 권한 원칙에 어긋난다. 실제 적용 코드: `scripts/provision.sh`의 `install -d`, `chown`, `chmod`.

## 3. ACL(Access Control List)

기본 owner/group/others 권한만으로는 홈 전체를 공개하지 않으면서 **특정 그룹만 통과**시키기 어렵다. ACL은 사용자/그룹별로 추가 접근 규칙을 준다.

```bash
setfacl -m g:agent-common:--x /home/agent-admin
getfacl -p /home/agent-admin
```

첫 줄은 공통 그룹이 홈 목록을 열람할 수는 없지만 `$AGENT_HOME` 아래의 허용된 경로에 진입하도록 만든다. `d:g:agent-common:rwx` 같은 **default ACL**은 디렉토리 밑 새 파일/폴더가 생성될 때 적용할 권한의 틀이다. 파일 생성 요청 모드에 따라 실제 권한의 상한이 결정되므로 새 파일도 `getfacl`로 확인한다. `setfacl -b`와 `setfacl -k`는 이전 ACL을 지워 뜻하지 않은 접근 허용이 남지 않게 한다.

## 4. SSH와 UFW: 서로 다른 보안 계층

**SSH**는 암호화된 원격 접속 서비스이고, `sshd`가 설정에 따라 특정 TCP 포트에서 접속을 받는다. `Port 20022`는 기본 포트 22 대신 사용할 포트를 지정한다. 이것만으로 침입을 막지는 못하지만 무차별 기본 포트 스캔을 줄인다. `PermitRootLogin no`는 원격 Root 로그인을 금지하여 특권 계정 공격 경로를 줄인다.

**UFW**는 호스트 방화벽을 다루는 도구다. `default deny incoming`으로 원칙적으로 수신을 차단하고 `allow 20022/tcp`, `allow 15034/tcp`로 필요한 두 서비스만 예외를 둔다. SSH 설정과 UFW는 **별개**이므로 양쪽 모두 맞아야 접속된다.

`sshd -t`는 문법 검사, `sshd -T`는 유효 설정 확인, `ss -ltnp`는 실제 LISTEN 소켓 확인, `ufw status verbose`는 방화벽 규칙 확인에 사용한다. **원격에서 방화벽부터 바꾸면 접속이 끊길 수 있으므로** `scripts/secure-network.sh`는 콘솔에서만 적용하도록 독립시켰다.

## 5. 소켓, LISTEN, PID의 관계

TCP 서버는 IP 주소와 포트에 **바인딩(bind)**한 뒤 연결을 기다린다. 이 상태가 `LISTEN`이며, `0.0.0.0:15034`는 모든 IPv4 인터페이스에서 포트 15034를 수신한다는 뜻이다.

```bash
ss -H -ltnp 'sport = :15034'
```

- `-l`: 듣는 소켓, `-t`: TCP, `-n`: 숫자 주소/포트, `-p`: 소켓 소유 프로세스, `-H`: 머리글 제외.
- 앱 프로세스가 존재한다고 반드시 포트가 열려 있는 것은 아니다. 반대로 포트가 열려 있어도 **다른 프로그램**일 수 있다. `monitor.sh`는 두 조건과 소켓의 PID를 연결해 확인한다.
- 앱이 `0.0.0.0:15034`에 바인딩했는지는 실제 배포 검증에서 별도로 확인한다.

## 6. 환경 변수와 `exec`

**환경 변수**는 부모 프로세스가 자식에게 전달하는 `이름=값` 설정이다. `export AGENT_PORT=15034`라고 지정하면 실행 파일이 동일한 포트를 참조할 수 있다. 디렉토리를 코드에 여러 번 직접 적으면 경로가 어긋날 수 있으므로 `AGENT_HOME`으로 묶는다.

`run-app.sh`의 `. agent-app.env`는 현재 셸에서 설정 파일을 실행하여 환경을 채우는 문법이고, `exec "$app"`는 현재 셸 프로세스를 앱으로 교체한다. **cron은 로그인 프로필을 자동으로 읽지 않기 때문에**, `monitor.sh`에는 포트/로그 경로 기본값도 있다. `env | grep '^AGENT_'`로 값이 전달됐는지 확인할 수 있다.

## 7. Bash 스크립트의 핵심 문법

| 문법 | 역할 | 실제 예 |
|---|---|---|
| `#!/usr/bin/env bash` | Bash로 실행 | 모든 `.sh` 파일 첫 줄 |
| `set -euo pipefail` | 처리하지 않은 명령 실패, 미정의 변수, 파이프 오류를 조기에 알림 | `monitor.sh` 시작 부분 |
| `"$variable"` | 경로의 공백과 패턴 해석 방지 | `"$LOG_FILE"` |
| `$(command)` | 명령 출력을 변수에 저장 | `pid=$(...)` 계열 |
| `[[ 조건 ]]`, `(( 계산 ))` | 문자열/파일 비교, 정수 계산 | 로그 크기 비교 |
| `function_name() { ...; }` | 반복 로직 함수화 | `warn_if_high`, `fail` |
| `||`, `if ...; then` | 예상 가능한 실패를 분기 처리 | 프로세스 없음/방화벽 상태 |
| `>>`, `2>&1` | 파일에 추가, 표준 오류 합치기 | 로그/cron 설정 |

`set -e`는 모든 실패를 무조건 종료시키는 단순한 스위치가 아니다. `if` 조건문처럼 **의도적으로 검사한 실패**는 종료하지 않는다. 그래서 방화벽 실패는 `if ...; then ... else [WARNING]` 형태이고, `fail` 호출은 명확히 `exit 1`을 수행한다.

## 8. 자원 사용률과 임계값

- **CPU:** `vmstat 1 2`는 약 1초 간격의 두 표본을 출력한다. 두 번째 행에서 `id`(유휴 비율, 15열)를 읽고 `100-id`로 사용률을 계산한다. 첫 행은 부팅 이후 평균이어서 순간 사용률로 사용하지 않는다.
- **메모리:** `free -b`의 `available`은 애플리케이션에 제공할 수 있는 가용량의 추정치로, 회수 가능한 캐시를 포함한다. `100 × (total-available)/total`로 계산한다. 단순 `used/total`과 값이 다를 수 있다.
- **디스크:** `df -P /`는 **루트 파일시스템**이 사용하는 공간의 비율을 보여준다. 메모리와 달리 운영체제 캐시 개념을 빼는 값이 아니다.
- **임계값:** `awk`로 실수 값을 비교하고 **초과(`>`)**할 때만 경고를 출력한다. CPU 20%, MEM 10%, 디스크 80% **정확히 같은 값**은 경고하지 않는다.

측정치는 서버 전체 상태이며 제공 앱만의 CPU/메모리 사용량을 뜻하지 않는다. 서버 전체를 관제하는 것이 미션 요구사항이다.

## 9. 로그, 회전, `flock`과 cron

**로그(logging)**는 그 시점의 상태를 시간과 함께 파일에 남기는 것이다. 장애를 재현하지 못해도 과거 데이터를 읽을 수 있다. 이 프로젝트는 날짜·PID·CPU·MEM·DISK_USED를 한 줄로 기록한다.

파일이 계속 커지면 디스크를 소모하므로 로그 **회전(rotation)**이 필요하다. `monitor.sh`는 한 행을 더했을 때 10MiB를 넘으면 오래된 번호를 밀어내고 `monitor.log.1`부터 `.9`까지 보관한다. 보너스의 7일 압축/30일 삭제 정책과 다르다.

`flock`은 **파일 잠금**을 통해 겹치는 두 실행이 동시에 로그를 회전하지 못하게 한다. `cron`은 시계에 따라 명령을 실행하는 스케줄러다.

```cron
* * * * * /home/agent-admin/agent-app/bin/monitor.sh >> /var/log/agent-app/cron.log 2>&1
```

`* * * * *`는 분·시·일·월·요일 각각 매번 일치하므로 **매분** 실행한다. `monitor.log`는 정상 수치, `cron.log`는 출력·실패 원인을 담는다. `crontab -u agent-admin -l`로 실제 등록 상태를 확인한다. 실패한 프로세스가 자동으로 재시작되지는 않는다. 이는 요구사항 밖의 기능이다.
